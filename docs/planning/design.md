# skillassert.com: v1 design

Status: approved by the owner on 2026-10-29, with the v1 additions listed in section 2. The phased plan (ticket 09)
follows from this document. Source of decisions: `map.md` (standing decisions), `grilling-log.md`
(rounds 1 to 3), `research/01` (hosting facts). Vocabulary: `GLOSSARY.md`. Decisions marked **(my call)** were made by
the author of this document, not by the owner, and can be overturned without re-opening the design.

## 1. Intent

A quiz site where a learner picks a topic and a tier, answers ten multiple-choice questions with or without a
timer, and afterwards reads explanations for what they missed. Questions are generated by an LLM ahead of time and
reviewed by one admin before learners see them. The owner builds it to run a real product end to end and to learn
backend and infrastructure concepts along the way, and to practise modern Angular.

## 2. Goals, non-goals, anti-goals

**Goals (v1 is done when all of these are live at skillassert.com)**

- Public homepage with a category tree; a quiz can be started from any topic at any tier.
- Quiz player with the learner's settings: topic, tier, format (single, multi, mixed), timed or not.
- Results page with score, per-question explanations for missed questions, bookmark, flag and note actions.
- One trial quiz without an account; sign-in with Google or an email magic link; trial data carried into the new
  account, including trials taken by returning learners.
- Bookmarks, flags and notes for signed-in learners; "Retry what I missed" and "Quiz my bookmarks" quiz sources.
- Topic progress (best score per topic and tier) and a next-tier nudge on results.
- Product metrics from server-side events: a trial-to-account funnel and per-topic usage on the admin dashboard.
- Per-question statistics (accuracy, flag rate) for the admin.
- Keyboard-first, accessible player with free navigation and an overview grid; light and dark themes.
- "Download my data" next to account deletion.
- Admin area: review queue, question search and edit, generation batches, category management, import.
- Generation pipeline: admin-triggered batches, LLM draft pass, stronger-model verify pass, drafts into the queue.
- Launch content: English, five IT topics, three tiers, about 20 approved questions per topic and tier.
- Running cost at or below EUR 20 per month; EUR 0 while free tiers hold.

**Non-goals (out of v1, room reserved)**

- Payments and premium enforcement; learner authoring UI; curated fixed quiz sets.
- Languages other than English; native mobile apps; offline mode; leaderboards, sharing, comments.

**Reserved for v1.1 (decided 2026-10-29, not built in v1)**

- Question revision history on admin edits (trigger-based undo and diff).
- Quiz length option (5, 10 or 20 questions).
- Admin-curated learn-more links per topic.
- General feedback form and "was this explanation helpful?" thumbs as a flag reason.
- Practice mode with immediate feedback per question (changes the `answer_question` contract).

**Anti-goals (v1 has failed even if it works)**

- Any unreviewed LLM question reaching a learner.
- A learner-facing path that stops working when the VPS is down.
- Infrastructure heavy enough to stall the product (orchestrators, multiple environments, message brokers).
- A data model that needs a migration to add an author or a premium flag later.

## 3. Constraints

- Solo developer, 5 to 8 hours a week, first public slice targeted about six weeks after building starts.
- Supabase Free: 500 MB database, no backups, project pauses after a week without database activity, default
  mailer limited to 2 emails per hour to team addresses, Edge Functions capped at 150 s. Pro ($25 plus VAT) is out
  of budget, so the design stays within Free.
- VPS: about 2 vCPU and 4 GB (Hetzner entry plan if orderable, else OVH VPS-1), EU location.
- EU-based owner and audience: EU regions for Supabase and the VPS; privacy policy, terms and account deletion.
- Single admin (the owner) in v1.

## 4. Architecture

```
 Browser (Angular SPA on Cloudflare Workers static assets, prerendered home and category pages)
   |                                   |
   | Supabase JS (anon key + user JWT) | HTTPS, bearer = Supabase JWT (admin only)
   v                                   v
 Supabase Free (EU)                  NestJS "content service" (Docker, Caddy TLS, EU VPS)
   Postgres + RLS + functions          generation batches, verify pass, import, bulk admin,
   Auth (Google, email, anonymous)     account deletion, health job
   Storage (unused in v1)                |  server-only Postgres role (bypasses RLS)
         ^-------------------------------'
 LLM vendor API (key lives only on the VPS)   Object store for nightly dumps   Uptime + error tracking
```

Rules (ADR 0001, ADR 0002):

- The learner path never calls the NestJS service. Catalog, quizzes, attempts, bookmarks, flags, notes and auth go
  through Supabase under row-level security; starting a quiz, saving an answer and submitting are Postgres functions.
- The NestJS service owns everything that needs a secret or bypasses learner permissions: generation, verify,
  import, bulk admin actions, account deletion. Single-record admin edits (approve, reject, edit a question, manage
  categories) go directly to Supabase under an admin policy **(my call)**: it avoids duplicating CRUD in the API.
- Six modules with the same names on both sides: Catalog, Question Bank, Quiz Play, Learner, Identity, Admin. A
  module owns its tables; other modules reference them by id only. Enforced in the monorepo with Nx tags.

## 6. Frontend

- Latest stable Angular; standalone components; signals with signal inputs and outputs; OnPush; zoneless; built-in
  control flow; strict TypeScript; lazy routes per module.
- State: services exposing signals. NgRx SignalStore only for the quiz player store (timer, position, answers,
  bookmarks, flags, submission state, persistence of answers through the Postgres function).
- Angular Material + CDK; light and dark themes from Material theme tokens, following system preference with a
  manual toggle; Material components wrapped in `libs/web/ui` only where repeated.
- Accessibility baseline from the first screen: keyboard-first player (number keys select, Enter advances), real
  radio and checkbox groups with labels, visible focus and focus management on navigation, `prefers-reduced-motion`
  honoured, colour contrast checked in both themes. Playwright flows run with keyboard only once.
- Routes: `/` home, `/c/:slug` category (nested slugs allowed), `/quiz/start?topic=&tier=` settings, `/quiz/:attemptId`
  player, `/quiz/:attemptId/results`, `/me`, `/me/bookmarks`, `/me/attempts`, `/me/notes`, `/auth/*`, `/admin/**`,
  `/privacy`, `/terms`.
- Guards: `authenticated` (any session, anonymous included), `permanent` (non-anonymous; required for `/me/**`),
  `admin` (profile role admin, re-checked server-side by RLS).
- Prerender at build time: `/`, `/c/**` for published categories (route params fetched from Supabase with the anon key
  during the build). Everything else client-rendered. No runtime SSR.
- Prerendered pages carry the category tree and static copy only; stock counts and format availability load
  client-side after hydration, so they are never stale. Category changes reach the prerendered pages through an
  admin "Publish site" action: the API triggers the web deploy workflow on GitHub (`workflow_dispatch`) with a
  scoped token, or the next merge rebuilds. The build reads categories from the production project, which the
  daily health job keeps awake **(my call)**.
- Forms: reactive forms in the admin area; the quiz player uses its store, not forms.
- Error and empty states are part of every data-bound screen: loading, loaded, empty, error.

## 7. Identity

- Supabase Auth. Providers: Google and email magic links (one-time sign-in links, no passwords, so there is no
  password-reset flow to build); anonymous sign-ins. Manual identity linking enabled.
- Email **(my call, research 03)**: Supabase custom SMTP pointed at Mailjet's free plan (6,000 a month, 200 a day,
  SMTP included, custom domain with validation, EU-only data centres, no card, no approval gate). Fallbacks: SMTP2GO
  (Amsterdam) or Resend (sends from Ireland, account data in the US). A dedicated sending subdomain with SPF, DKIM
  and DMARC records on Cloudflare DNS and a `no-reply@` From address. Supabase applies 30 emails an hour once custom
  SMTP is on, adjustable under Rate Limits.
- `profile` row per auth user, created by a trigger on `auth.users` insert: `user_id` (PK, FK auth.users), `display_name`,
  `role` (`learner` | `admin`, default learner), timestamps. The owner is promoted to admin once by SQL.
- Admin checks: RLS policies call `is_admin()` (SECURITY DEFINER, reads `profile.role` for `auth.uid()`); the NestJS
  service verifies the Supabase JWT and loads the profile role **(my call: role lives in `profile`, not in JWT
  metadata, so there is one source of truth and no claim-sync code)**.
- Anonymous learners carry the `is_anonymous` claim. They may: start exactly one attempt (enforced inside
  `start_quiz`), answer and submit it, bookmark and flag questions from it. They may not: create notes, list
  attempts or bookmarks pages (`/me/**` requires `permanent`). The results page shows a sign-up prompt.
- Upgrade: the client calls `updateUser({email})` or `linkIdentity({provider: 'google'})` on the anonymous
  session. Confirmed by ticket 06 from the Auth server source: both paths update the same `auth.users` row, so the
  id and every row keyed by `auth.uid()` survive. Facts the builder must honour: after `updateUser` the user stays
  anonymous until the confirmation link is used, so the results page says "check your email to finish"; the stored
  JWT keeps `is_anonymous: true` until the next refresh, so the client refreshes the session after confirmation or
  the OAuth callback before loading `/me/**`; use a current supabase-js (a PKCE regression affecting this flow was
  fixed in July 2026); re-test the open upstream issues auth#1525 and auth#2847 in the Identity phase.
- Conflicts: an email or Google identity that already belongs to another account returns `email_exists` and leaves
  the anonymous user untouched; there is no server-side merge. v1 carries such trials over with a claim-token merge
  (round 5, Q43): while anonymous, the client obtains a one-time claim token for its attempt (`claim_trial()`);
  after signing in to the existing account it calls `merge_trial(token)` (SECURITY DEFINER), which re-keys that
  attempt and its bookmarks and flags to the caller. Possession of the token is the proof of ownership; tokens
  expire after 24 hours. The results page says "Sign up or sign in to keep this result".
- RLS for permanent-only data (notes, `/me/**` reads) uses the documented pattern: a restrictive policy on
  `(select (auth.jwt()->>'is_anonymous')::boolean) is false`.
- Abuse: anonymous sign-ins default to 30 an hour per IP; Cloudflare Turnstile (free, mostly invisible) guards the
  trial start **(my call)**. The API's daily job deletes anonymous users older than 30 days; cascades remove their
  rows **(my call)**.
- "One trial" is enforced softly: the anonymous session itself plus a local-storage marker. Clearing storage
  yields a new anonymous user and another trial; accepted (round 1, Q7).
- Account deletion: `DELETE /me` on the NestJS service removes the auth user with the service role; all learner
  tables cascade on `user_id`.

## 8. Data model (Postgres, `public` schema)

Enums: `tier` (novice, intermediate, senior), `question_kind` (single, multi), `question_state` (draft, approved,
rejected), `author_type` (system, learner), `visibility` (free, premium), `quiz_format` (single, multi, mixed),
`attempt_status` (in_progress, submitted, expired), `batch_status` (queued, running, done, failed), `verify_status`
(unverified, pass, doubtful), `flag_reason` (wrong_answer, unclear, typo, other).

| Table | Module | Columns (beyond id, created_at, updated_at) |
|---|---|---|
| `category` | Catalog | `parent_id` (self FK, null = root), `slug`, `name`, `description`, `sort_order`, `is_published`; unique (`parent_id`, `slug`). A topic is a category with no children. |
| `question` | Question Bank | `topic_id` FK category, `tier`, `kind`, `prompt`, `explanation`, `state`, `author_type` (default system), `author_id` (nullable), `visibility` (default free), `batch_id` (nullable FK), `verify_status`, `verify_note`, `prompt_version`, `flag_count` (open flags), `pulled_at` (nullable), `approved_at`, `approved_by`, `search` (generated tsvector over prompt, explanation and option texts, GIN index) |
| `option` | Question Bank | `question_id` FK, `text`, `is_correct`, `sort_order`. Check on approve: single kind has exactly one correct, multi kind at least one, every question 3 to 6 options. |
| `generation_batch` | Question Bank | `topic_id`, `tier`, `kind`, `requested_count`, `focus` (nullable), `status`, `model_draft`, `model_verify`, `prompt_version`, `produced_count`, `cost_usd`, `error`, `created_by`, `started_at`, `finished_at` |
| `flag` | Learner | `question_id`, `learner_id`, `reason`, `comment`, `resolved_at` (nullable); unique (`question_id`, `learner_id`) |
| `bookmark` | Learner | PK (`learner_id`, `question_id`) |
| `note` | Learner | `learner_id`, `title`, `body_md`, `question_id` (nullable), `topic_id` (nullable), `search` tsvector |
| `attempt` | Quiz Play | `learner_id`, `topic_id`, `tier`, `format`, `timed`, `duration_seconds` (nullable), `question_count`, `status`, `started_at`, `expires_at` (nullable), `submitted_at` (nullable), `score` (nullable) |
| `attempt_question` | Quiz Play | PK (`attempt_id`, `position`), `question_id`, `option_order` (uuid[] as served), `selected_option_ids` (uuid[] nullable), `is_correct` (nullable), `answered_at` |
| `profile` | Identity | `user_id` PK, `display_name`, `role` |
| `event` | Admin | `kind` (trial_started, quiz_started, quiz_submitted, signup, trial_converted, trial_merged, flag_created), `learner_id` (nullable), `attempt_id` (nullable), `topic_id` (nullable), `tier` (nullable), `props` jsonb. Written only by functions and triggers; readable by admins. |

Triggers: maintain `question.flag_count` from open flags; when open flags from three distinct **permanent** learners
exist on an approved question, set `state = draft` and `pulled_at = now()` (it leaves the bank until re-approved).
Flags from anonymous sessions are stored and shown in the review queue but never count toward the pull, because
anonymous sessions are free to create **(my call)**. Resolving a
flag (admin) sets `resolved_at`; re-approving clears `pulled_at`.

Visibility in v1: every query that serves learners filters `visibility = 'free'`; the column exists so premium is a
policy change, not a migration.

Text format **(my call)**: `prompt`, `option.text` and `explanation` are CommonMark markdown with fenced code blocks
allowed, because most launch topics need code in the question. Every screen renders them through one sanitizing
markdown component with syntax highlighting (`libs/web/ui`); the `search` columns and the de-duplication step use a
plain-text projection with markdown stripped. The generation JSON schema carries the same markdown strings.

Views: `topic_stock` (approved questions per topic, tier and kind; feeds the homepage counts and the admin
dashboard), `option_public` (option without `is_correct`), `question_stats` (per question: times served, times
answered, accuracy, open and total flags, average time where derivable from consecutive `answered_at` values;
admin only), `learner_topic_progress` (per learner, topic and tier: attempts, best score, last attempt; each learner
sees their own rows), `funnel` (per day and topic: trials started, quizzes submitted, sign-ups, trial conversions
from `event`; admin only).

## 9. Row-level security and functions

Learners (`authenticated` role, anonymous included) may:

- select published `category`; select `topic_stock`.
- select `question` only through the functions below or when it belongs to one of their attempts; never select
  `option.is_correct` (no grant on `option`; `option_public` is granted).
- insert and select their own `bookmark` and `flag`; permanent learners also insert, update, delete their own `note`.
- select their own `attempt` and `attempt_question` (results are read through `get_attempt_result`).

Admins (via `is_admin()`) may read everything and update `question`, `option`, `category`, `flag.resolved_at`.

Functions (SECURITY DEFINER, exposed as RPC; every one re-checks `auth.uid()`):

- `start_quiz(topic_id, tier, format, timed, source) -> attempt_id, questions[]`: rejects a second attempt for an
  anonymous user (`trial_used`); samples 10 approved free questions matching the format (mixed draws from both
  kinds); errors with `not_enough_questions` below 10; shuffles option order and persists it; sets `expires_at =
  now() + count x allowance` when timed (60, 90, 120 s per question by tier) plus 10 s grace; returns prompts and
  options without correctness. Count and allowances are table-driven constants **(my call)**. `source` is `bank`
  (default), `missed` (questions this learner answered wrongly in submitted attempts for the topic and tier) or
  `bookmarks` (this learner's bookmarked questions in the topic); both need a permanent account, force mixed format,
  and run with fewer than 10 questions when the pool is smaller, down to a minimum of 3 **(my call)**. The function
  writes a `trial_started` or `quiz_started` event.
- `answer_question(attempt_id, position, selected_option_ids)`: saves progressively so a refresh loses nothing;
  rejected after `expires_at` or after submission.
- `submit_attempt(attempt_id) -> result`: grades all-or-nothing per question (selected set equals correct set),
  stores `score`, marks `submitted` (or `expired` when past `expires_at`), writes a `quiz_submitted` event, returns
  the result.
- `get_attempt_result(attempt_id) -> result`: score, each question with the learner's selection, the correct
  option ids and the explanation; only for a submitted or expired attempt owned by the caller.
- `claim_trial() -> token` and `merge_trial(token)` (section 7); `merge_trial` writes a `trial_merged` event.
- `export_my_data() -> jsonb`: the caller's profile, attempts with their questions and answers, bookmarks, flags
  and notes, downloaded by the client as a JSON file; a Postgres function so the learner path stays off the VPS
  **(my call)**.
- `is_admin()`. Triggers on `auth.users` write `signup` (insert, non-anonymous) and `trial_converted`
  (`is_anonymous` true to false) events.

Explanations for a bookmarked question are visible when the learner has a submitted attempt containing it;
otherwise the bookmark shows the prompt and "take a quiz to reveal" **(my call)**.

## 10. Quiz Play and Learner behaviour

1. Learner opens a topic, picks tier, format and timed; the settings screen offers only formats whose stock for the
   topic and tier (from `topic_stock`) covers a full quiz, and explains why a format is unavailable. The app then
   calls `start_quiz`.
2. Player shows one question at a time with position, bookmark and flag actions, free movement back and forth, and
   an overview grid of answered, unanswered and bookmarked questions that also serves as the pre-submit check;
   timed quizzes show the remaining time computed from `expires_at`; answers are saved on each change through
   `answer_question`.
3. On submit, or when the timer runs out, the app calls `submit_attempt` and navigates to results.
4. Results: score, missed questions expanded with explanation and correct options, "show all" toggle, bookmark,
   flag and "take a note" on each question, a "Retry what I missed" button (source `missed`, permanent learners), and
   a next-tier nudge when the score is 80% or better and a higher tier has stock **(my call on the threshold)**.
   Anonymous learners see a sign-up prompt that promises to keep the result.
5. `/me` shows topic progress from `learner_topic_progress` (best score per topic and tier, last attempt) and the
   account actions: download my data, delete account. `/me/attempts` lists past attempts with score and a link to
   results **(my call: small and makes carry-over visible)**; `/me/bookmarks` groups bookmarks by topic with a "Quiz
   me on these" button per topic (source `bookmarks`); `/me/notes` lists notes newest first with search, and a note
   editor with markdown preview. Topic pages show the signed-in learner's best score per tier.

## 11. Question Bank, generation and review

**Lifecycle**: `draft` (generated or imported) -> `approved` (admin) or `rejected` (admin). Three distinct open flags
pull an approved question back to `draft` with `pulled_at` set.

**Generation batch** (NestJS):

1. Admin submits topic, tier, kind, count and optional focus from `/admin/batches/new`; the API inserts a `queued`
   row. The `generation_batch` table is the job queue; a single in-process worker polls it **(my call: no Redis or
   broker on the VPS in v1; a broker is a later upgrade if batches ever contend)**.
2. Draft pass: the worker calls the LLM through a `QuestionGenerator` port with two adapters, Anthropic
   (claude-haiku-5-5 drafts, claude-sonnet-5-5 verifies) and OpenAI (gpt-6-luna drafts, gpt-6.1-sol verifies).
   Each call asks for five questions (configurable) with strict JSON-schema structured output defined in
   `libs/shared/domain`: prompt, kind, 3 to 6 options with correct marks, an 80 to 150 word explanation, tags and one
   line on why this tier, all text fields markdown. Reasoning effort at the vendor's lowest setting and a hard
   output-token limit per call. The stable instructions, examples and topic brief come first so they cache; the
   list of existing prompts to avoid comes last. A response that fails schema validation is retried once, then
   counted as failed. Prompts are versioned files; `prompt_version` is stored on the batch and each question.
   Calls run synchronously, three in flight, so a batch of 20 finishes in minutes and the admin sees progress; the
   vendors' batch APIs are not used.
3. De-duplication: a draft whose normalized prompt is more than 0.6 trigram-similar (`pg_trgm`) to an existing
   question in the same topic is dropped and counted **(my call)**.
4. Verify pass: the stronger model of the same vendor receives each draft and answers `pass` or `doubtful` with a
   note, reasoning effort low; stored on the question. Doubtful drafts are shown first in the queue with the note.
5. Drafts are inserted with `state = draft`; the batch records token usage and `cost_usd` per call from a price
   table in configuration. Cost caps, all configurable: a batch refuses to start when its estimate (requested count
   times the running average cost per question, or a conservative default) exceeds $2, stops when its actual cost
   does, and no batch starts once the calendar month's total passes $10. A spend limit set in the vendor console is
   the backstop against bugs such as a retry loop.
6. Vendor choice (ticket 07): the first batch for one topic and tier runs 20 questions through each adapter; the
   review queue hides the vendor until the admin has decided on each question; the admin then sets the default
   adapter in configuration and the other stays as a fallback.

**Import**: `POST /questions/import` accepts the same JSON schema as generation and inserts drafts (seeding,
hand-written content, migration between environments).

**Review queue** (`/admin/questions`): default view is drafts and flagged questions, flagged first by flag count,
then doubtful drafts, then by age. Search by id prefix or full-text over prompt, explanation and options; filters
by topic, tier, kind, state, verify status, batch. The edit screen changes prompt, options, correct marks,
explanation, tier and kind, resolves flags, and approves or rejects. Approval runs the option-shape check.

**Dashboard** (`/admin`): stock per topic, tier and kind from `topic_stock`, open flags, recent batches with status
and cost, the trial-to-account funnel and per-topic usage from `funnel`, and a link to the per-question statistics
table (`question_stats`, sortable by accuracy and flag rate) for spotting mis-tiered or weak questions.

**Categories** (`/admin/categories`): tree editor; a category with questions cannot gain children; unpublishing hides
it from learners without touching questions.

## 12. NestJS content service

- Modules mirror the map: `question-bank` (batches, worker, import, verify), `identity` (JWT guard, admin guard,
  account deletion), `admin` (bulk approve or reject), `health`.
- Auth: bearer Supabase JWT verified against the project's JWKS; admin guard loads `profile.role`.
- Database access through the server-only connection (Supabase service role or a dedicated Postgres role);
  queries through a typed query builder or Prisma **(left to the builder; the schema is owned by Supabase
  migrations, so the API's tooling must not generate migrations)**.
- Endpoints: `POST /batches`, `GET /batches`, `GET /batches/:id`, `POST /questions/import`, `POST /questions/bulk`
  (approve or reject many), `DELETE /me`, `GET /health` (touches the database; doubles as the Supabase anti-pause
  signal when called by the uptime monitor).
- Configuration by environment variables; secrets only on the VPS; structured JSON logs to stdout.

## 13. Environments, delivery, operations

- Local: Supabase CLI starts Postgres, Auth, Studio in Docker; `supabase/migrations` holds every schema change;
  `seed.sql` loads categories and a handful of questions; the API runs with a local env file; the web app points at
  the local stack.
- Production: one Supabase project (EU region), one VPS, the web app as Cloudflare Workers static assets, DNS on
  Cloudflare (nameservers moved from Porkbun; Porkbun stays registrar). No staging.
- Web hosting **(my call, research 04)**: Cloudflare Workers static assets deployed with Wrangler from GitHub Actions;
  static requests are free and unlimited, SPA fallback is `not_found_handling: single-page-application`, matching
  prerendered HTML files are served first. Cloudflare's docs now say "Start new projects with Workers"; Pages stays
  the fallback if the prerender plus fallback combination misbehaves in phase 0. Custom domain on the Cloudflare zone.
- CI on every pull request: install, `nx affected` lint, test and build, Playwright flows (trial quiz, sign-up
  carry-over, admin approve) against a local Supabase and the API started in the job.
- CD on merge to `main`, in order: apply pending Supabase migrations (expand-then-contract rule so the running
  app keeps working), build and push the API image to GitHub Container Registry (public package, so the VPS pulls
  without a token) and `docker compose pull && up -d` on the VPS over SSH, deploy the web build with Wrangler. No
  vital job runs on a GitHub schedule: scheduled workflows auto-disable after 60 days without repository activity.
- VPS: Docker Compose with `caddy` (image `caddy:2`, automatic TLS for `api.skillassert.com` via Let's Encrypt with
  ZeroSSL fallback, persistent `/data` volume for certificates, the only container publishing ports 80 and 443) and
  `api` (no published ports; Caddy reaches it on the Compose network, which matters because Docker-published ports
  bypass ufw); SSH keys only, ufw, unattended upgrades; images rebuilt by CI only.
- Backups: nightly `pg_dump` from the VPS to Backblaze B2, EU Central (Amsterdam), S3-compatible, 10 GB free, no
  card at sign-up, 14-day lifecycle; a vendor other than the one hosting the frontend on purpose; Cloudflare R2
  (`eu` jurisdiction) is the fallback. Monthly restore drill into local Supabase **(my call, research 04)**.
- Monitoring **(my call, research 04)**: Better Stack free plan for uptime checks on the web app and `GET /health`
  plus a heartbeat on the backup job (UptimeRobot Free has no heartbeats); Sentry Developer plan in the EU region
  (Frankfurt, 5k errors a month, 30-day lookback) with `@sentry/angular` and `@sentry/nestjs`.
- Analytics: Cloudflare Web Analytics, cookieless by Cloudflare's own statement (no legal review done); its default
  setup excludes EU and UK visitors, so that switch is turned off at setup. No consent banner.
